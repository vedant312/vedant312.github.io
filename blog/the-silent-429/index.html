Field notes · X API

The Silent 429

The X API answers in HTTP status codes, and it overloads them. The worst offender is 429: it has three independent causes, one of which — since X went pay-per-use — now means “you are out of money for the month,” not “slow down for fifteen minutes.” Read it as the second and your campaigns sit at “Running,” send nothing, and never fire an alert. Here is the real error taxonomy, what the docs say versus what we measured, and the rules that keep a status code from lying to you.

Why you are here

The dashboard says “Running.” Nothing is sending. Nothing errored.

Every campaign is green. The workers are up, the tokens are valid, the last log line is an ordinary “rescheduled.” And not a single message has gone out in hours. There is no exception in your tracker, no alert in your channel, nothing red anywhere — because from your code's point of view, nothing failed. It just keeps politely waiting fifteen minutes and trying again, forever.

What happened is that the X API returned a 429, your code read it as a rate-limit window, and rescheduled. But that particular 429 did not mean “too fast.” It meant “you have spent your monthly allowance.” No amount of waiting will clear it until the billing cycle rolls, and it will not announce itself any differently from the transient kind. This post is about why one status code carries that much ambiguity, and how to stop it from failing you silently.

01 · The mental model

The status code is the wire, not the reason

The X v2 API leans hard on HTTP status codes, and a handful of them each cover several unrelated situations. A 403 is “valid auth, but not allowed” — which could be a protected account, an app without the right access level, or a suspended user. A 404 is “gone” — deleted, never existed, or (on some endpoints) an auth failure wearing a not-found costume. And 429, the one that will actually hurt you, means at least three different things.

The status code tells you the class of outcome. It does not tell you the reason, and — critically — it does not tell you whether waiting will help. Two 429s can be identical on the wire and require opposite responses: back off and retry, or stop and alert a human. If your handler branches on the status code alone, it is guessing.

02 · One 429, three counters

Three independent limits, one indistinguishable status

X's own documentation is explicit that rate limits and billing are independent: you can be well within your rate limits and still be blocked for spend, or burn through a rate limit at no extra cost. What the docs do not put in one place is that three separate counters all surface as the same 429:

CounterWindowWhat clears itRight response
Per-endpoint window15 min (some /sec)The reset timestampBack off, retry
Posting / write cap24 hours (per-user and per-app)Midnight-ish rollingWait hours, spread load
Usage / billing capMonthlyThe billing cycleStop. Alert a human.

The window limit is the friendly one, and it comes with instructions. Every response carries three headers: 

x-rate-limit-limit:     900      # ceiling for this window
x-rate-limit-remaining: 847      # what's left
x-rate-limit-reset:     1705420800   # unix seconds until it refills

A genuine window 429 hands you x-rate-limit-reset — a near-future instant — and the documented recovery is simply to wait until then and retry, with exponential backoff if you keep colliding. Note that the window limits are doubled: every endpoint keeps a separate counter for per-user tokens (OAuth 1.0a / OAuth 2.0 user context) and for app-only bearer tokens. POST /2/tweets, for instance, is 100 per 15 minutes per user but 10,000 per 24 hours per app — two different ceilings you can hit for the same call.

03 · The error body

You cannot trust the sentence, only the shape

X's v2 errors are shaped after RFC 9457 Problem Details — a JSON object with a machine-readable type URI, a short title, a human detail, and sometimes a status: 

{
  "title":  "Invalid Request",
  "detail": "The `query` parameter is required.",
  "type":   "https://api.x.com/2/problems/invalid-request"
}

The type URI is the part you should branch on — it is stable and enumerable: invalid-request, resource-not-found, not-authorized-for-resource, client-forbidden, usage-capped, rate-limit-exceeded, and a generic about:blank. The detail sentence is for humans, and it is a trap: it is free text, it changes, and on some endpoints it embeds user-supplied values.

Format is not a contract

The v2 errors only approximate Problem Details — the shape is inconsistent across endpoints. Some return title/type/status/detail; others hand you message/title/detail/type; the older {"errors":[{"code":88,"message":"…"}]} array still appears on rate-limit responses. Parse defensively: read the fields that exist, key your logic off type and the HTTP status, and never assume every endpoint agrees on field names.

04 · Prose is not a category

Classify on structure, or a username will page you

Here is the mistake, because we made it. Failure classification substring-matched the human message for words like quota, credit, rate limit, daily, monthly. It worked in testing. Then a routine 403 went out whose detail embedded the recipient's handle — a handle that happened to contain the substring “daily.” The 403 classified as credit exhaustion, paged the on-call, and — worse — armed a sixty-minute throttle on “credit alerts” for that sender, muting the alerts that would have been real.

The fix is not a better word list. The word list is the bug. The API already told us the category structurally: the response was a 403 with a forbidden-family type, and our own client had captured status_code and a normalized error_code at the boundary — the classifier just never read them. A failure's category is a function of its status code and problem type, never of its prose. The moment you find yourself lowercasing an error message and calling in on it, you have written a bug that a customer's username will trigger.

05 · A status-code field guide

What each code really means on this API

CodeDocumentedWhat it also means here
400Bad request — invalid JSON, malformed query, missing paramsYour query builder emitted something X won't parse. See §07 — a valid-shaped but empty query does not 400.
401Invalid or missing credentialsOn a data provider, a bad key. Distinct, and useful — see the note below.
403Valid auth, no permissionProtected account, wrong access level, suspended user — or a usage error that didn't get a 429. Do not infer “this recipient is protected” from a 403 during an outage.
404Resource doesn't exist / deletedSometimes an auth failure — some providers answer a bad token with 404 “Could not authenticate you.”
409Conflict (filtered stream has no rules)Very often “already done” — treat an idempotent create's 409 as success, or your reconciler reports failures forever.
429Rate limit or usage cap exceededThe three counters of §02. Read the reset header before you decide it's transient.
5xx500 / 502 / 503 / 504 — wait and retryGenuinely transient usually — but see the provider note: an over-quota upstream key can surface as a 500.

The status code can fingerprint an upstream key. When we ran X data through a third-party provider, the HTTP status told us the key's exact state without a body: a bad key returned 401, an over-quota key returned 500, a missing parameter 400, and a bad handle 404. The 500 is the sneaky one — it reads as “their server is broken,” but it meant “rotate the key.” We only found it because the primary provider hit its quota and we failed over for the first time at volume, exposing a key that had been quietly over its limit for days.

06 · Pay-per-use changes the stakes

A 429 can now mean “out of money,” and a retry loop is a bill

In February 2026 X made pay-per-use the default. New projects no longer get a free tier or a flat Basic/Pro subscription; reads and writes are billed per call — on the order of a fraction of a cent for a post read, about a cent for a user or follower read, a cent and a half to create a post, and a steep premium for posts carrying a link. (Those numbers move; treat them as the shape, not the contract, and check the current sheet.) Older subscription tiers still exist for grandfathered accounts, but the direction is unambiguous: every call has a price, and there is a monthly ceiling on your spend.

This is what turns the silent 429 from an annoyance into an incident. The usage/billing cap is one of the three counters, and when you hit it the API returns the same 429 as a fifteen-minute window — but no amount of backoff clears it, and a naive “retry on 429” loop now does two harmful things at once: it sends nothing and, on any endpoint that bills on request rather than success, it can keep spending while it spins. A runaway retry is a runaway bill.

The distinguishing test

A window 429 carries a near-future x-rate-limit-reset. A usage-cap 429 generally does not — the reset is absent, or so far out it's meaningless. So the rule is mechanical: if a 429 has no near-future reset, stop retrying and alert. Do not reschedule it into the same fifteen-minute loop as a window limit.

07 · 200 is not “it worked”

Success codes are not validation results

Two different 200s will lie to you on this API, in opposite directions.

The first: a malformed query can succeed. Hand a search endpoint a query that is syntactically wrong and you will often get 200 OK with zero results — not a 400. There is no server-side signal separating “nothing matched your valid query” from “your query was nonsense,” so if you let users compose raw queries, front-end validation is the only guard you have against a silent empty state. A success code is not a validation result.

The second: a 200 can carry an errors array. When you request several resources at once and some are unavailable — a deleted post in a lookup, a suspended user in a batch — X returns 200 with the resources it could resolve in data and the ones it could not in a sibling errors array. Code that checks only the HTTP status treats a partial failure as a total success and silently drops the missing half.

The habit that covers both: on a read, assert on the shape you expected, not the status. Did you get the number of records you asked for? Is there an errors key? A 200 means the request was well-formed enough to answer — nothing more.

08 · The silent failure, start to finish

How “Running” and “sending nothing” coexist for hours

Here is the incident that this whole post is really about, assembled. A sender hit the monthly usage cap. X returned 429 with a body that carried neither the word “credit” nor the word “limit” — a bare UsageCapExceeded-shaped payload — and, being a cap rather than a window, no useful reset header. Our scheduler's rate-limit branch caught the 429, did the correct thing for a window limit — pushed the whole sender queue past the reset and fell back to a fifteen-minute retry when the header was absent — and, deliberately, stayed neutral to the failure streak so a transient limit wouldn't pause a healthy account.

Every one of those behaviors is right for a window limit and wrong for a cap. The result: the campaign read Running, the queue rescheduled itself every fifteen minutes, the streak breaker never tripped, and no alert fired — for hours — because the one branch that would have alerted was the branch we didn't take. The signal was there the whole time; the code sorted it into the wrong bin.

The fix, in one sentence

Classify the 429 body distinctly — a usage/billing cap is not a window limit — and give the cap its own branch that alerts and stops instead of rescheduling into the retry loop. A limit that no amount of waiting can clear must never be handled by waiting.

09 · Keep the body

The wrapper that threw away the evidence

None of the above is recoverable after the fact if your HTTP layer discards the response body on error. Ours did, on one deployed branch — the provider wrapper returned (None, resp.status_code) and dropped resp.text — so by the time an alert fired, the only thing left was “a 429 happened,” with no type, no title, no way to tell a window limit from a cap from a billing error. The alert was technically working and completely useless.

Persist the triple — HTTP status, the type URI, and the raw body — on every non-2xx, at the boundary where you still have them. A normalized error_code is worth computing there too, so nothing downstream is tempted to re-derive the category from prose (§04). The body is small; the ability to answer “what actually happened” is not.

10 · Rules

What not to do

  • ✕Never treat every 429 as a transient window limit. Read x-rate-limit-reset; no near-future reset means a 24-hour or usage cap — stop and alert, don't loop.
  • ✕Never classify a failure by substring-matching the message. A username containing “daily” is not a billing event. Branch on status + problem type.
  • ✕Never discard the response body on a non-2xx. A wrapper that returns (None, status) makes a window limit, a cap, and a billing error indistinguishable after the fact.
  • ✕Never read 200 as “it worked.” A malformed query 200s with zero results, and a multi-resource 200 can carry a partial errors array.
  • ✕Never infer a per-recipient fact from a 403 during an outage. A blanket forbidden condition will flag innocent recipients as “protected” and poison the data you make decisions on later.
  • ✕Never assume the field names. Some endpoints send title/detail/type, some message/…, rate limits send {"errors":[{"code":88}]}. Read what exists.
  • ✓Do budget for per-call billing. Under pay-per-use a retry loop is a spend loop; a circuit breaker on the cap protects the bill as much as the account.
  • ✓Do give the usage cap its own branch that alerts and pauses, separate from the window-limit reschedule path.
  • ✓Do treat an idempotent 409 as success so your reconciler stops reporting a “failure” that already happened.
11 · For your LLM

The context to paste before you build this

We build against this API with heavy AI assistance, and an assistant will cheerfully write “retry on 429 with backoff” because that is the textbook answer — and it is exactly the bug. The context below states what is true of this specific API, phrased as prohibitions, because that is what survives being summarized into a plan three steps later.

X API — error, limit & billing invariants
# X API (v2) — error, rate-limit, and billing rules for this codebase

## Facts the docs underspecify
- A 429 has THREE independent causes: a per-endpoint 15-minute window limit,
  a 24-hour posting/write cap (enforced per-USER and per-APP separately), and
  the MONTHLY usage/billing cap. Rate limits and billing are INDEPENDENT.
- The ONLY in-band tell between them is x-rate-limit-reset. A window 429 carries
  a near-future reset; a 24h/usage cap 429 does not (absent or far away).
- Errors approximate RFC 9457 problem+json {type, title, detail, status}, with
  type URIs like https://api.x.com/2/problems/usage-capped. The format is
  INCONSISTENT across endpoints (some use message/...); rate-limit 429s still
  use the legacy {"errors":[{"code":88,"message":"Rate limit exceeded"}]}.
- A 200 is not success: a malformed search query returns 200 + zero results
  (no 400), and multi-resource reads return 200 with a partial `errors` array.
- Since Feb 2026 the default is PAY-PER-USE: reads and writes bill per call.
  A usage-cap 429 means "out of monthly spend," not "slow down."

## Hard prohibitions
- NEVER handle every 429 by waiting/retrying. If there is no near-future
  x-rate-limit-reset, STOP and alert a human; do not reschedule into the loop.
- NEVER classify a failure by substring-matching the human message/detail.
  Branch on (http_status, problem_type_uri) and a normalized error_code only.
  A 403 whose detail embeds a username containing "daily" is NOT a billing error.
- NEVER discard the response body on a non-2xx. Persist (status, type, raw body);
  a wrapper returning (None, status) makes the three 429s indistinguishable later.
- NEVER treat 200 as "it worked" on a search or a multi-resource read.
- NEVER infer "this recipient is protected/blocked" from a 403 during an outage;
  a blanket forbidden condition poisons per-recipient inference.
- NEVER assume field names or that a create is not idempotent — treat a 409 on an
  idempotent create as success.

## Required shape
- Classify every failure as (http_status, problem_type_uri) -> category. Keep the
  raw body for forensics. Compute the category ONCE, at the HTTP boundary.
- Two 429 branches: window (has near reset) -> backoff+retry; cap (no reset) ->
  alert + pause the sender, never auto-retry.
- Under pay-per-use, add a spend circuit breaker: a retry loop is a bill.

## Before any high-volume or paid call
State the per-call cost and the monthly cap. A loop that retries a capped 429
forever spends money and sends nothing while every dashboard reads "Running".

The one that matters most is the first prohibition. An assistant will not spontaneously know that a 429 can be un-waitable, because the status code does not say so. You have to tell it which 429s are walls, not speed bumps.

12 · What's documented vs. what we measured

Where the line is

In the interest of not passing off scars as specifications: the header names, the status-code meanings, the problem-details shape, the partial-errors behavior, and the fact that rate limits and billing are independent are all in X's published docs. The three-counters-behind-one-429 framing, the usage-cap 429 arriving without a reset, the pay-per-use prices, and every incident above are measured — from our own traffic and from the docs as they stood in September 2026. Access levels and prices on this platform change on a schedule of their own, so before you design around a number here, confirm it against the current developer docs. The shapes are stable; the quantities are not.

Written up because the failure that started it was invisible by construction: nothing errored, nothing paged, and a green dashboard sat on top of a queue that had not moved in hours. The most expensive bugs are the ones the system is too polite to mention.

If a status code has lied to you the same way — or if you know the current shape of a limit that moved since this was written — that is exactly why it's public.
