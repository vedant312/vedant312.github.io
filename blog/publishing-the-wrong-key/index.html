Field notes · X Chat API

Publishing the Wrong Key

We integrated X's end-to-end encrypted chat API, and along the way we published a server identity key onto an account a person was actively using in the X app. It broke their chat, changed the safety number every one of their contacts sees, and there is no endpoint to undo it. Here is how the API actually works, what the docs don't tell you, and the one rule that would have saved us.

Written after ~5 weeks of integration · All findings measured against live traffic · Account details withheld · Updated 25 Sep 2026 with X's later replies

Why you are here

Your DM integration went blind and you don't know why

If you run anything that reads a user's X DMs through GET /2/dm_events, you may have noticed conversations quietly disappearing from your inbox. They aren't deleted. They moved. X Chat conversations are end-to-end encrypted, and the legacy DM events endpoint does not return them.

The fix is not a parameter. It is a separate API — /2/chat/* — with its own auth model, its own subscription system, its own rate limits, its own SDK, and a cryptographic model you have to understand before you write a line of code. It is additive: plaintext DMs still only come from /2/dm_events, so you will end up running both.

This post is the guide we wanted five weeks ago. It is written in the order the decisions actually arrive, and it is honest about the one we got wrong.

01 · The mental model

Two kinds of key, and only one of them matters to you

Almost every mistake in this space comes from collapsing two different things into the word "key". Keep them apart:

An identity key belongs to a person (or a bot). It is long-lived, it is published to X so others can find it, and it is what a conversation key gets wrapped to. A conversation key belongs to a thread. It is what actually decrypts message ciphertext, and it is sealed to each participant's newest published identity at the moment the key is made.

Two consequences fall straight out of that, and the whole architecture rests on them:

  • There is no forward secrecy. Conversation keys are static and wrapped to long-lived identity keys. That is precisely why a PIN unlock can recover years of history — and why losing an identity key loses the history with it. X also never re-seals an old conversation key to a newer identity: we fetched a thread's full key history and found keys from before an identity change still sealed only to the older identity. Each identity opens exactly the history that was sealed to it.
  • Decryption needs the conversation key, not the identity. Once you hold a conversation key, you never need the identity again. We verified this against live data: a Chat instance reporting is_unlocked=False decrypted real messages when the conversation keys were supplied explicitly.

That second point is the single most useful fact in this post. Hold onto it — it is what makes the mistake in section 6 unnecessary as well as harmful.

02 · The fork in the road

Two identity paths, and you must pick exactly one per account

X supports two ways for code to have an identity on an account, and the docs present them as two sections of a getting-started guide rather than as a fork with a wrong branch. They are a fork with a wrong branch.

X's own staff put it plainly when we asked: the server path "isn't meant to sit alongside the consumer app's PIN/Juicebox keys on the same account." Their later, more precise answer is the one to build on: the current identity is always the published version with the highest public_key_version (a millisecond timestamp). There is no separate "active" marker. New conversation keys must be sealed to each participant's newest version, and older versions only verify old signatures. So the moment you publish, your key is the one every new conversation is sealed to — and if it has no Juicebox registration, the app's PIN unlock tries it first and fails.

X gave the same answer to another developer who was publishing a fresh key on every user sign-in and hit the same failure: one identity owner per account. Either your backend owns the key, for a bot account nobody opens X Chat on in the app, or the app owns it and your backend unlocks that existing version. And if you do publish, persist the private key for that version — refetching public keys never gives it back.

One-way door

POST /2/users/:id/public_keys is rate-limited to 5 per 24 hours, and that limit is the least of it. There is no documented public API to retire or supersede a published key version. Treat every call as permanent.

03 · Integration

What the endpoints actually do

Existing DM scopes are enough — if your app already holds dm.read and friends, you do not need users to re-consent. The API surface is small. The traps are not.

The API never returns plaintext

Every event comes back as an encoded_event ciphertext blob. There is no server-side "give me the text" mode. If your product needs plaintext, you must decrypt it yourself, which is what section 4 is about.

Listing conversations returns more than you asked for

GET /2/chat/conversations returns the account's whole DM inbox, not only encrypted threads. Measured on a live account, 4 of 12 sampled conversations had zero chat events — they were legacy DMs surfacing in the same list. Probe before you assume an id is an X Chat conversation.

Ask for fields explicitly, and know which ones are expansions

participant_ids, member_ids and admin_ids are expansions, not conversation fields. Requesting them as fields risks a 400 on every call. For a 1:1 the participant is derivable anyway — the conversation id is {min}-{max} of the two user ids.

Data-loss trap

On GET /2/users/:id/public_keys, always send an explicit public_key.fields. The docs do not promise what an omitted value returns, and an empty response reads to your code as "this account has no PIN-backed identity". The natural UI remedy for that — "set X Chat up again" — rotates the identity and destroys the user's history. A missing query parameter should not be able to cause that.

A juicebox_config does not prove a PIN backup exists

The reverse trap. GET /2/users/:id/public_keys returned a juicebox_config on the key our backend published, even though our request sent nothing but the public key and X confirmed that version has no Juicebox registration. The field's presence is not evidence that a PIN can unlock that version. Decide which version to unlock from the key blobs you actually need to open, not from which entries carry a config.

The key-event list is page-scoped

GET /2/chat/conversations/:id/events returns message events in data and, separately, meta.conversation_key_events. That key list covers the page, not the conversation's full key history. Measured: max_results=1 returned 2 key events where a full walk returned 5. Fine for a single call; a history backfill must page and union them.

Rate limits

These are from X's launch announcement rather than the published API reference, so treat them as observed rather than contractual. The events read is the binding constraint:

EndpointWindowDaily
GET /2/chat/conversations50 / 15 min1,000
GET /2/chat/conversations/:id/events30 / 15 min1,000
POST /2/chat/conversations/:id/keys10 / 15 min100
POST /2/chat/conversations/:id/messages25 / 15 min500
POST /2/users/:id/public_keys—5

An hourly account-wide sweep fights these limits immediately. Realtime delivery is not a nice-to-have here; it is how the design stays inside the budget.

One message, two different ids

This one cost us a day. X publishes two ids for the same event, and which one you get depends on how it arrived. The REST harvest returns a snowflake; the webhook returns a UUID. Store whichever the transport handed you and you will write the same message twice, under ids that can never be matched. 

harvested via REST   2093644612959346688      (snowflake)
delivered by webhook d07bb3d2-a407-428e-...   (uuid)
overlap              none

Both ids are actually present on every event, inside the envelope. Which brings us to a detail worth knowing for its own sake.

The envelope is not encrypted

encoded_event is a Thrift binary struct whose leading fields are plaintext metadata. You can read them with no key and no SDK — base64-decode and walk the struct: 

field 1  event id (snowflake)
field 2  event id (uuid)
field 3  sender x_id
field 4  conversation id
field 5  conversation token
field 6  created_at, epoch ms

The message body is encrypted; who sent it, in which conversation, and when, are not. That is worth understanding before you describe the system to users as end-to-end encrypted without qualification. It is also useful: canonicalising on field 1 is what fixed our duplicate-id problem.

04 · Decryption

Where decryption happens, and why it isn't your server

This is the part the docs leave you to work out, and getting the shape right is what makes the whole thing both possible and defensible.

The naive design is: hold the user's identity on the server, unlock everything server-side, decrypt at will. It is also the design that pushes you toward publishing a key you shouldn't. The correct shape moves the identity to the browser and keeps only conversation keys on the server.

The SDK detail that makes this work

The Chat SDK offers a batch decryptEvents(events, signing_keys) and a singular decryptEvent(blob, conversation_keys, signing_keys). The batch call is the recommended API and it is the wrong one for this design: it has no slot for keys, so it derives them from KeyChange events inside the same list — which requires an unlocked identity.

The singular form takes conversation keys explicitly. That is the entire basis for unattended server-side decryption without ever holding a user's identity. Loop the singular call; ignore the ergonomics advice.

Traps in the browser half

  • juicebox_config arrives as an object; createChat wants a string. It calls JSON.parse internally, so passing the parsed object coerces to "[object Object]" and throws a SyntaxError. Every unlock fails with no network request at all, which is a miserable thing to debug.
  • There is no realm-token endpoint. We looked for one for days. The tokens are already inside juicebox_config.token_map — an array of {key: realmId, value: {address, token}}, not an object keyed by realm. getAuthToken is just that lookup. The JWTs are scoped to {x_id}:{key_version} and expire after one hour, so fetch them at submit time, never at mount.
  • Extract one blob at a time. extractConversationKeys returns a flat {version: key} map with no conversation attached. Batch the call and pair results with your pending list afterwards, and you get a cartesian product — conversation A's key filed against conversation B, under a version its ciphertext will never match. Blobs are few. Loop them.
  • Signing keys must cover both participants. Supply only the inbox owner's and the other party's messages fail verification and get silently dropped.
  • Pick the key version from the blob, never by walking the list. An account can have several Juicebox-backed versions — every time the owner sets X Chat up again without recovering, the app creates a new one with its own PIN. A PIN unlocks only its own version, and a conversation key opens only with the version it was sealed to. That version is readable in the key blob's plaintext Thrift header, so read it and send the PIN to that one config. We first shipped "try the configs oldest first", and it produced both symptoms on a real account: the current PIN was rejected by the old version as "wrong PIN", and the old PIN unlocked the old version, which could open none of the recent blobs.
Destroys the identity

The PIN guess budget is finite, and exhausting it destroys the key material permanently. Read the remaining count from the SDK and show it. The budget belongs to one version's registration: the realm tokens are scoped to {x_id}:{key_version}, and every attempt counts against that version alone. So stop on the first invalid_pin, and never retry the same PIN across an account's other published configs — it cannot succeed on a version it doesn't belong to, and each try spends a guess there.

A note on the Python package

The pip distribution is chatxdk but the module it provides is chat_xdk, and it ships a native extension. "Installed" and "importable" are genuinely different states — pip show succeeding proves nothing. Worse, a long-running process caches its view of site-packages, so a package installed while your server is running stays invisible until you invalidate the import cache or restart.

05 · Realtime

Account Activity does not carry chat events

If you already run DM webhooks, you have an Account Activity (AAA) subscription and you will reasonably assume it covers chat. It does not, and nothing tells you — you simply receive nothing and conclude your webhook is broken.

We settled it with a controlled A/B on a live account: one AAA subscription active, zero Activity API subscriptions, two messages sent.

Chat events are delivered through POST /2/activity/subscriptions — per user and per event type, with a webhook_id and a filter: {user_id}. You can reuse your existing registered webhook; you do not need a second one.

The credential is different per operation

This is undocumented and it is what made the endpoint look like a missing entitlement for weeks. Our first attempt used the user token for the list call, got a 401, and concluded the app wasn't approved. The app was fine. The credential was wrong.

OperationCredentialNotes
GET /2/activity/subscriptionsApp bearerUser token returns 401
POST /2/activity/subscriptionsUser tokenScope comes from the user's grant
DELETE .../{id}App bearerFall back to user token; undocumented

Two smaller notes: a 409 on create means "already subscribed" — treat it as success or your reconciler will report failures forever. And the id is spelled subscription_id on create but id in some listings.

Caps and cost, which change the architecture

Account Activity on pay-per-use allows 3 unique subscriptions. Not 3,000 — three. We had ten subscription rows failing with a generic 4xx for weeks before someone checked the count endpoint and found the cap was simply full. If your error handling collapses every 4xx into one code, you will never see this.

The Activity API allows 1,500 on self-serve. If you subscribe four event types per account, that is a ceiling of 375 accounts, and you should know that number before you design around it. chat.received and dm.received bill at $0.010 per delivered event; chat.sent and dm.sent are free.

Because delivery bills per event, your teardown path is a financial control, not a cleanup nicety. If a user disconnects and your code fails to delete the subscription, X keeps delivering and you keep paying. Never mark an account unsubscribed based on a subscription listing you failed to read.

06 · The mistake

We published a key that bought us nothing

Here is the decision, as it was actually written down at the time. We framed it as a fork between two identity routes:

(a) backend-registered keypair via POST /2/users/:id/public_keys — forward-only, backend can read → compatible with the features that need server-side plaintext; (b) the user's PIN unlocks full history but must stay on-device, leaving the backend blind → incompatible with the product. Choose (a).

The reasoning felt sound. Several product features needed plaintext server-side. Path (b) appeared to make that impossible. So we took path (a) — the bot/server path — on accounts belonging to real people who use X Chat in the app.

Then, during testing, a publish went through on one of those accounts.

The symptoms arrived immediately and were not subtle. The owner's PIN stopped working in the X app, which reported "Registration does not exist". Every one of their contacts saw a security-code change notification. All three key versions were still returned by GET /2/users/:id/public_keys, and the underlying key material was intact — but the app would not use it.

X later confirmed the mechanism. The app treats the highest version as current and tries that version's Juicebox registration first when the owner enters their PIN. Our published key was the highest and had no registration, so the app reported that it did not exist. The owner's two app-created versions were untouched; the app just never reached them.

Four things made it worse than it had to be

  • We flagged the irreversibility and did it anyway. Our own notes said "irreversible, 5/24h, no revoke" from the very first week. Writing a warning down is not the same as building a guard.
  • We tested on a live account that someone actually uses. There was no reason it could not have been a throwaway. The bot/server path exists precisely for accounts nobody uses in the app.
  • The publish came from our test environment. When we finally traced it, the only identity row marked as published sat in the test environment's database, stamped the same second as the key version on X. A test deployment holding real account tokens made an irreversible change to a real account. Anything that can call a one-way endpoint is production, whatever its hostname says.
  • A safety default lied to us. The publish flag defaulted to off, and a backfill script documented as "actually publish" called the register function without it — so it minted local identities while logging success as though it had registered. When the thing that is supposed to publish doesn't, and something else does, you lose the ability to reason about what happened.

And the part that still stings

When we eventually built the design properly — browser unlock, conversation keys sealed server-side, unattended decryption afterwards — we deleted the publishing code entirely. Not because it was risky. Because nothing needed it.

Receiving events needs a subscription. Decrypting needs conversation keys. Neither requires a key of yours to be published on the account. Path (a) and path (b) were never really a trade-off between capability and safety — we just hadn't understood the SDK well enough to see that the safe path did everything.

The lesson, in one line

We spent an irreversible action, a user's chat access, and their contacts' trust — and received exactly zero capability in return.

07 · Recovery

Where the account stands now

We reported this on X's developer forum and their staff engaged quickly and helpfully. The first answers, in the week of the incident:

  • There is no documented public API to retire a published key version or force the app back onto an earlier registration.
  • Re-registering from the app is the usual recovery path, but prior encrypted conversations are not guaranteed to remain readable afterwards.
  • We were advised not to wipe or overwrite key material from our side until they confirm the recovery steps.
  • We were advised to stop entering the PIN in the app while it shows the error, since that can consume the guess budget without fixing anything.

So the account was frozen. Worth saying explicitly: "frozen" took real work. Background workers that harvest, decrypt, retry, and demote key state are all mutations of key material, and doing nothing manually is not the same as nothing happening. If you find yourself here, stop your workers, not just your hands.

Three weeks later: the suggested fix, and why we paused it

X came back with the cause (section 6) and a fix that needed nothing from their side: at the app's PIN prompt, choose Forgot PIN and set a new one. The app would publish a newer version with a real Juicebox registration, that version would become the highest, and X Chat would work again — with one more security-code change for every contact. History encrypted to the app-created versions "should remain readable if the app already recovered those keys during earlier PIN attempts, but this isn't guaranteed."

It did not play out that way. Forgot PIN did not offer a new PIN. It opened a "Forgot Passcode" screen warning that without a passcode or a linked device X cannot retrieve the encrypted messages, with exactly two buttons: Reset Chat and Go Back. We stopped and asked before pressing anything.

The answer: Reset Chat starts a fresh Chat identity on that device, and should be treated as wiping access to the existing encrypted conversations in the app — including the ones only the older app-created versions could open. It is not a surgical removal of our key. X offered to look for a safer path first if we sent the current key versions.

What the key versions showed

A read-only dump of the published versions, next to our own key rows, settled several things at once:

  • Three versions: two created by the X app (one from late 2025, one from two days before the incident) and ours, the highest.
  • Every conversation key we had stored for the account was sealed to our version — exactly what "new keys go to the newest version" predicts.
  • We still hold the private key for that version. So the conversations sealed to it remain recoverable on our side whatever happens in the app. The history that is at risk is the older history behind the two app-created versions.

X's staff also spelled out the design they would have wanted from the start: if a backend needs to act as an account that uses X Chat in the app, it should unlock the app's existing, highest version with the owner's PIN — Chat(config).unlock(pin) — rather than register a separate key.

This section is still open. We are sending X the key versions and asking whether our version can be retired so the app falls back to its own, whether the older Juicebox registrations survive a reset, and what happens to messages on X's servers and on other signed-in devices. We will update this post with the outcome — including if the answer is that the older history is unrecoverable, because that is the more useful result to publish.

08 · Rules

What not to do

Every item here corresponds to something that actually went wrong, either for us or in a way we came close enough to see clearly.

  • ✕Never publish an identity key onto an account a person uses in the X app. Not once, not "just to test". There is no undo.
  • ✕Never forget that the highest public_key_version is current. Anything you publish immediately becomes the version every new conversation is sealed to.
  • ✕Never retry a PIN in a loop, or across an account's several key configs. Each version has its own PIN and its own finite budget, and exhausting it is permanent.
  • ✕Never treat a juicebox_config as proof of a PIN backup. X returned one on our published key, which has none.
  • ✕Never let a test environment hold real account tokens next to a one-way endpoint. Ours is where the publish came from.
  • ✕Never treat a failed or empty key lookup as "no PIN backup". That path's remedy rotates the identity and loses history — for what is usually an expired token.
  • ✕Never assume your DM webhook covers chat. Verify with a controlled send; silence looks identical to a broken receiver.
  • ✕Never collapse every 4xx into one error code. A full subscription cap is indistinguishable from a bad token if you do.
  • ✕Never mark an account unsubscribed from a listing you failed to read. X keeps delivering and billing.
  • ✓Do keep the identity in the browser and send only conversation keys to your server. It is both safer and sufficient.
  • ✓Do keep one identity owner per account — the app, or a bot backend, never both. If you ever publish, persist that version's private key.
  • ✓Do send a PIN only to the version the blobs are sealed to, read from the blob itself.
  • ✓Do canonicalise event ids on the envelope's snowflake, so REST and webhook deliveries of the same message agree.
  • ✓Do test irreversible operations on a throwaway account whose loss you would not mind explaining to its owner.
09 · For your LLM

The context to paste before you build this

We built this integration with heavy AI assistance, and the mistake in section 6 is one an assistant will make readily. Not because it is careless, but because X's documentation presents the two identity paths as equally available options, and nothing in the reference marks the publish call as irreversible. An assistant reading those docs will cheerfully reach for the path that gives the backend more capability.

So describing the API is not enough. The context has to state what is true, not just what is possible — and it has to be phrased as prohibitions, because that is what survives being summarised into a plan three steps later.

Paste this into your CLAUDE.md, your .cursorrules, or the top of your prompt before asking for any X Chat work.

X Chat integration — invariants
# X Chat (X's E2EE DM API) — rules for this codebase

## Facts that are not obvious from the docs

- Every /2/chat/* payload is ciphertext. The API has no plaintext mode.
- An account may have SEVERAL published identity key versions. The CURRENT one is
  always the highest public_key_version (a ms timestamp); there is no other
  "active" marker. New conversation keys are sealed to each participant's newest
  version only. The X app unlocks the highest version first.
- Each app-created version has its OWN Juicebox registration, its OWN PIN and its
  OWN guess budget. A PIN unlocks only its own version.
- Conversation keys are static and wrapped to long-lived identity keys. There is
  no forward secrecy, and X never re-seals an old conversation key to a newer
  identity. Each identity opens exactly the history sealed to it — and losing
  one loses that history.
- A juicebox_config on a public_keys entry does NOT prove that version has a
  Juicebox registration. X returns one on server-published keys that have none.
- Decryption requires CONVERSATION keys, not an identity. A Chat instance
  reporting is_unlocked=false decrypts correctly when conversation keys are
  passed explicitly.
- Account Activity (AAA) subscriptions do NOT deliver chat.* events. Chat
  realtime requires POST /2/activity/subscriptions, per user AND per event type.
- The envelope is not encrypted: encoded_event's leading Thrift fields expose
  event ids, sender id, conversation id and timestamp with no key.

## Hard prohibitions

- NEVER call POST /2/users/:id/public_keys for an account that a human uses in
  the X app. Publishing makes your key the account's CURRENT X Chat identity: it
  invalidates the owner's PIN, changes the safety number every contact sees, and
  X exposes NO endpoint to retire or supersede a key version. It cannot be undone.
- Publishing is NOT required to receive events (that needs a subscription) and
  NOT required to decrypt (that needs conversation keys). If a design appears to
  require publishing, the design is wrong. Re-read the decryption path.
- NEVER retry a PIN automatically, and NEVER retry the same PIN against another
  key config. Each version's guess budget is finite and separate; exhausting it
  destroys that identity permanently. Read the key version each pending blob is
  sealed to (plaintext in the blob's Thrift header), send the PIN ONLY to that
  version's config, stop on the first invalid_pin, and surface the remaining
  count.
- ONE identity owner per account: the official app, or a bot backend that never
  opens X Chat in the app. Never both. If you publish for a bot, persist that
  version's private key; refetching public keys cannot recover it.
- Test environments must not hold real account tokens where they can reach a
  one-way endpoint.
- NEVER treat an empty or failed public_keys response as "this account has no
  PIN backup". The UI remedy for that state rotates the identity and destroys
  history. Always send an explicit public_key.fields, and treat a lookup failure
  as a lookup failure.
- NEVER mark an account's subscriptions removed based on a listing that failed
  to load. X keeps delivering and billing per event.
- NEVER send the user's PIN to the backend, log it, or persist it.

## Required implementation shape

- The identity is unlocked in the BROWSER. The browser extracts conversation
  keys and sends ONLY those to the backend, which seals them at rest. The
  backend decrypts unattended afterwards and never holds the PIN or identity.
- Use the SINGULAR decrypt call that accepts conversation keys explicitly. The
  batch call has no slot for keys and derives them from KeyChange events, which
  requires an unlocked identity.
- Extract conversation keys ONE BLOB AT A TIME. The extract call returns a flat
  {version: key} map with no conversation attached; batching and pairing
  afterwards produces a cartesian product across conversations.
- juicebox_config arrives as an OBJECT; createChat calls JSON.parse internally
  and needs the STRING form. Its token_map is an ARRAY of
  {key: realmId, value: {address, token}}. Those realm JWTs expire in ONE HOUR —
  fetch them at submit time, never at mount.
- Supply signing keys for BOTH participants or the other party's messages fail
  verification and are dropped.
- Canonicalise event ids on the envelope's snowflake field. REST returns a
  snowflake, the webhook returns a UUID, for the same message.
- Activity API credentials differ PER OPERATION: GET uses the app bearer (user
  token 401s), POST uses the user token, DELETE uses the app bearer with the
  user token as fallback. A 409 on create means already-subscribed — success.

## Before any irreversible call

Stop and ask the human. Irreversible here means: publishing a public key,
deleting a Juicebox registration, or anything that rotates an identity. State
plainly that it cannot be undone and name what breaks for the account owner.

The last block is the one that matters most. An assistant will not spontaneously recognise that a routine-looking POST is a one-way door, because nothing in the API's shape says so. You have to tell it which doors are one-way.

10 · Open questions

What we still don't know

  • Whether the older history survives a reset. Partly answered. X says Reset Chat loses it in the app, and we confirmed that old conversation keys are never re-sealed to a new identity. Still open: whether the older versions' Juicebox registrations survive a reset, so the old PIN could recover that history later on some device, or whether they are removed with it.
  • Whether a passcode change creates a new version. Our reading of the SDK is that changing the PIN on a signed-in device keeps the same version and only re-wraps the backup, while Forgot PIN, Reset Chat, or setting up without recovery creates a new one. X has not confirmed it.
  • Whether unlocking an older version is supported. A third-party client can unlock an older app-created version with its own PIN and read the history sealed to it. We have asked whether that is a supported path or whether only the current version is meant to be recoverable.
  • Which call actually published. Answered: the published identity row lives in our test environment's database, registered the same second as the key version on X (section 6). The exact code path in that deployment is the one piece we have not reconstructed.
  • Whether the delete credential is stable. We try the app bearer and fall back to the user token because we could not determine which X actually wants.
  • The real rate limits. The numbers in section 3 come from a launch announcement, not the API reference. They have held for us. They are not a contract.

Written up because we could not find this anywhere while we needed it. Every measurement here came from live traffic on accounts we own, with the owner present. Account identifiers, app ids and org details are deliberately omitted.

If you are mid-integration and something here saved you a week — or if you know the answer to anything in section 10 — that is exactly why it is public.
