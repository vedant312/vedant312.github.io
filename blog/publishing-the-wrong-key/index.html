Field notes · X Chat API

Publishing the Wrong Key

We integrated X's end-to-end encrypted chat API, and along the way our backend published its own identity key onto an account a person was actively using in the X app. It broke their chat, changed the safety number every one of their contacts sees, and there is no endpoint to undo it. This is how the API actually works, what the docs don't tell you, everything X's staff told us while we dug out — and the one rule that would have saved us.

Written after ~6 weeks of integration · Measured against live traffic · Updated 26 Sep 2026

Why you are here

Your DM integration went blind and you don't know why

If you run anything that reads a user's X DMs through GET /2/dm_events, you may have noticed conversations quietly disappearing from your inbox. They aren't deleted. They moved. X Chat conversations are end-to-end encrypted, and they do not appear in the legacy DM lookup endpoints or DM webhooks.

There is no switch to turn this off. X's staff have been explicit: you cannot disable X Chat for an account or a conversation and fall back to legacy DMs. The only way to see those conversations is a separate API — /2/chat/* — with its own auth rules, its own subscription system, its own rate limits, its own SDK, and a cryptographic model you have to understand before you write a line of code. It is additive: plaintext DMs still only come from /2/dm_events, so you will end up running both.

This post is the guide we wanted six weeks ago. It is written in the order the decisions actually arrive, it is honest about the one we got wrong, and it records what X told us on their developer forum while we recovered, because most of it is written down nowhere else.

01 · The mental model

Two kinds of key, and the rules that bind them

Almost every mistake in this space comes from collapsing two different things into the word "key". Keep them apart:

An identity key belongs to an account. It is long-lived, it is published to X under a public_key_version (a millisecond timestamp), and it is what conversation keys get sealed to. A conversation key belongs to a thread. It is what actually decrypts message ciphertext.

An account can have several published identity versions at once. These rules, all confirmed by X's staff, decide what happens between them:

  • The highest version is the current one. There is no separate "active" marker. The official app uses the highest version, and the API enforces it: a conversation key must be sealed to each participant's highest version, or POST /2/chat/conversations/:id/keys returns INVALID_IDENTITY_KEY_PAIR.
  • Older versions are read-only history. They still verify old signatures and still open the conversation keys that were sealed to them. They never receive new ones.
  • X never re-seals an old conversation key to a newer identity. We fetched a thread's full key history and found keys from before an identity change still sealed only to the older identity. Each identity opens exactly the history that was sealed to it.
  • Each app-created version has its own PIN. Its own Juicebox registration, its own PIN, its own guess limit. Changing the passcode on a signed-in device keeps the version. Forgot PIN, Reset Chat and setting up without recovery each create a new version and leave the older ones — and their PIN backups — in place.
  • A new version never deletes anything. Messages and key-change events are only removed by message or conversation deletion, disappearing-message expiry, or account deletion. After an identity change they are still on X's servers, just unreadable to any identity their conversation key wasn't sealed to.

Two consequences fall straight out of that:

  • There is no forward secrecy. Conversation keys are static and sealed to long-lived identity keys. That is why a PIN unlock can recover years of history — and why losing an identity loses the history sealed to it.
  • Decryption needs the conversation key, not the identity. Once you hold a conversation key, you never need the identity again. We verified this against live data: a Chat instance reporting is_unlocked=False decrypted real messages when the conversation keys were supplied explicitly.

That last point is the most useful fact in this post. Hold onto it — it is what makes the mistake in section 6 unnecessary as well as harmful.

02 · The fork in the road

One identity owner per account

X supports two ways for an account to have an identity, and the docs present them as two sections of a getting-started guide rather than as a fork with a wrong branch. They are a fork with a wrong branch.

X's staff described the two supported patterns in almost these words:

  • The official app owns the account. The app creates the Juicebox-backed version. Your backend unlocks that existing version with the owner's PIN — Chat(config).unlock(pin), with the juicebox_config for the highest version from GET /2/users/:id/public_keys — instead of publishing a competing key.
  • Your backend owns the account. Your server generates and keeps the private key and publishes it with POST /2/users/:id/public_keys — and that account never opens X Chat in the official app. This is for dedicated bot accounts.

There is no third option. X was explicit that there is no supported way to copy the official app's private key out to your backend, or to safely share one account between both. And publishing is not a one-off risk: another developer on the forum was generating and publishing a fresh key every time a user signed in, and their customers' decryption broke the same way ours did. Every publish creates a new, higher version, and every new conversation key goes to it.

One-way door

POST /2/users/:id/public_keys is rate-limited to 5 per 24 hours, and that limit is the least of it. There is no public API to retire or supersede a published version. Treat every call as permanent.

If you do own a bot account, publish a complete registration — public_key, signing_public_key, identity_public_key_signature, signing_public_key_signature and registration_method — and store the private key for that version. Refetching public keys never gives it back.

03 · Integration

What the endpoints actually do

Existing DM scopes are enough — if your app already holds dm.read and friends, you do not need users to re-consent. The API surface is small. The traps are not.

The API never returns plaintext

Every event comes back as an encoded_event ciphertext blob. There is no server-side "give me the text" mode. If your product needs plaintext, you must decrypt it yourself, which is what section 4 is about.

Listing conversations returns more than you asked for

GET /2/chat/conversations returns the account's whole DM inbox, not only encrypted threads. Measured on a live account, 4 of 12 sampled conversations had zero chat events — they were legacy DMs surfacing in the same list. Probe before you assume an id is an X Chat conversation.

Ask for fields explicitly, and know which ones are expansions

participant_ids, member_ids and admin_ids are expansions, not conversation fields. Requesting them as fields risks a 400 on every call. For a 1:1 the participant is derivable anyway — the conversation id is {min}-{max} of the two user ids.

What the key lookup can and cannot tell you

GET /2/users/:id/public_keys returns exactly five fields per version: public_key, signing_public_key, identity_public_key_signature, public_key_version and juicebox_config. public_key.fields accepts only those five, asking for anything else is a 400, and omitting the parameter returns the same five. Three things follow:

  • A juicebox_config proves nothing. X generates one on every read, for every version, whether or not a PIN backup exists for it. Our backend-published key had one, and it had no registration at all.
  • You cannot verify a registration is complete. signing_public_key_signature and registration_method are not readable. From the API, our incomplete version looked identical to the two complete app-created ones.
  • A failed or empty lookup is a lookup failure. Never read it as "this account has no PIN backup". The natural UI remedy for that state — "set X Chat up again" — creates a new version and strands the user's history behind their old PIN. Usually the real cause is an expired token.

The key-event list is page-scoped

GET /2/chat/conversations/:id/events returns message events in data and, separately, meta.conversation_key_events. That key list covers the page, not the conversation's full key history. Measured: max_results=1 returned 2 key events where a full walk returned 5. A history backfill must page and union them. Key events for older identity versions come back too, whichever version you hold.

Starting a conversation can fail for reasons you cannot fix

Other developers have hit this with Chat Agents: tapping Message created a keyless legacy type=direct conversation, the UI then showed it as read-only and unencrypted, and POST /2/chat/conversations/:id/keys returned UNAUTHORIZED_REQUESTING_USER in both directions. X's staff said it was not fixable from the client. One developer worked around it by creating a group conversation instead, built with the SDK's prepare_group_create rather than prepare_conversation_key_change. If key initialization fails in both directions with a well-formed payload, stop debugging your own code and report it with request ids.

Rate limits

These are from X's launch announcement rather than the published API reference, so treat them as observed rather than contractual. The events read is the binding constraint:

EndpointWindowDaily
GET /2/chat/conversations50 / 15 min1,000
GET /2/chat/conversations/:id/events30 / 15 min1,000
POST /2/chat/conversations/:id/keys10 / 15 min100
POST /2/chat/conversations/:id/messages25 / 15 min500
POST /2/users/:id/public_keys—5

An hourly account-wide sweep fights these limits immediately. Realtime delivery is not a nice-to-have here; it is how the design stays inside the budget.

One message, two different ids

This one cost us a day. X publishes two ids for the same event, and which one you get depends on how it arrived. The REST harvest returns a snowflake; the webhook returns a UUID. Store whichever the transport handed you and you will write the same message twice, under ids that can never be matched. 

harvested via REST   2093644612959346688      (snowflake)
delivered by webhook d07bb3d2-a407-428e-...   (uuid)
overlap              none

Both ids are present on every event, inside the envelope — which is worth knowing for its own sake.

The envelope is not encrypted

encoded_event is a Thrift binary struct whose leading fields are plaintext metadata. You can read them with no key and no SDK — base64-decode and walk the struct: 

field 1  event id (snowflake)
field 2  event id (uuid)
field 3  sender x_id
field 4  conversation id
field 5  conversation token
field 6  created_at, epoch ms

The message body is encrypted; who sent it, in which conversation, and when, are not. That is worth understanding before you describe the system to users as end-to-end encrypted without qualification. It is also useful: canonicalising on field 1 is what fixed our duplicate-id problem, and the same plaintext header of a key-change event tells you which identity version each participant's copy is sealed to.

04 · Decryption

Where decryption happens, and why it isn't your server

The naive design is: hold the user's identity on the server, unlock everything server-side, decrypt at will. It is also the design that pushes you toward publishing a key you shouldn't. The shape that works for app-owned accounts keeps the PIN and the identity in the browser and only conversation keys on the server.

The SDK detail that makes this work

X's Chat XDK offers a batch decryptEvents(events, signing_keys) and a singular decryptEvent(blob, conversation_keys, signing_keys). The batch call is the recommended one for an unlocked client: it pulls conversation keys out of the key-change events in the same list, verifies their signatures, and never lets the "latest key" move backwards. But it needs an unlocked identity to do that.

The singular form takes conversation keys explicitly, and that is the entire basis for unattended server-side decryption without the identity. One caveat worth knowing: the separate extractConversationKeys call adopts keys without checking the key-change signature — the SDK's own notes say so. If you extract in the browser, verify the key-change events before you store what they yield.

The most common "everything decrypts to nothing" report on the forum has the same cause every time: the caller passed only data to decryptEvents. The key-change events live in meta.conversation_key_events; concatenate both, set the identity and version, and supply signing keys for every participant.

Traps in the browser half

  • juicebox_config arrives as an object; createChat wants a string. It calls JSON.parse internally, so passing the parsed object coerces to "[object Object]" and throws a SyntaxError. Every unlock fails with no network request at all, which is a miserable thing to debug.
  • There is no realm-token endpoint. The tokens are already inside juicebox_config.token_map — an array of {key: realmId, value: {address, token}}, not an object keyed by realm. The JWTs are scoped to {x_id}:{key_version} and expire after one hour, so fetch them at submit time, never at mount.
  • Extract one blob at a time. extractConversationKeys returns a flat {version: key} map with no conversation attached. Batch the call and pair results with your pending list afterwards, and you get a cartesian product — conversation A's key filed against conversation B.
  • Signing keys must cover both participants. Supply only the inbox owner's and the other party's messages fail verification and get silently dropped.
  • Pick the version from the blob, never by walking the list. A PIN unlocks only its own version, and a conversation key opens only with the version it was sealed to. Read that version from the key-change event's plaintext header and send the PIN to that one config. We first shipped "try the configs oldest first", and on a real account it produced both symptoms at once: the current PIN was rejected by the old version as "wrong PIN", and the old PIN unlocked the old version, which could open none of the recent blobs.
Destroys the identity

The PIN guess budget is finite, and exhausting it destroys that version's key material permanently. The budget belongs to one version's registration, and every attempt counts against that version alone. Read the remaining count the SDK reports (guesses_remaining) and show it. Stop on the first invalid PIN, and never retry the same PIN across an account's other versions — it cannot succeed on a version it doesn't belong to, and each try spends a guess there.

A note on the Python package

The pip distribution is chatxdk but the module it provides is chat_xdk, and it ships a native extension. "Installed" and "importable" are genuinely different states — pip show succeeding proves nothing. A long-running process also caches its view of site-packages, so a package installed while your server is running stays invisible until you invalidate the import cache or restart.

05 · Realtime

Account Activity does not carry chat events

If you already run DM webhooks, you have an Account Activity (AAA) subscription and you will reasonably assume it covers chat. It does not, and nothing tells you — you simply receive nothing and conclude your webhook is broken.

We settled it with a controlled A/B on a live account: one AAA subscription active, zero Activity API subscriptions, two messages sent.

Chat events are delivered through POST /2/activity/subscriptions — per user and per event type, with a webhook_id and a filter: {user_id}. You can reuse your existing registered webhook.

The credential is different per operation

This is undocumented, and it made the endpoint look like a missing entitlement for weeks. Our first attempt used the user token for the list call, got a 401, and concluded the app wasn't approved. The app was fine. The credential was wrong.

OperationCredentialNotes
GET /2/activity/subscriptionsApp bearerUser token returns 401
POST /2/activity/subscriptionsUser tokenScope comes from the user's grant
DELETE .../{id}App bearerWe fall back to the user token

Two smaller notes: a 409 on create means "already subscribed" — treat it as success or your reconciler will report failures forever. And the id is spelled subscription_id on create but id in some listings.

Caps and cost, which change the architecture

Account Activity on pay-per-use allows 3 unique subscriptions. Not 3,000 — three. We had ten subscription rows failing with a generic 4xx for weeks before someone checked the count endpoint and found the cap was simply full. If your error handling collapses every 4xx into one code, you will never see this.

The Activity API allows 1,500 on self-serve. If you subscribe four event types per account, that is a ceiling of 375 accounts. chat.received and dm.received bill at $0.010 per delivered event; chat.sent and dm.sent are free.

Because delivery bills per event, your teardown path is a financial control, not a cleanup nicety. If a user disconnects and your code fails to delete the subscription, X keeps delivering and you keep paying. Never mark an account unsubscribed based on a subscription listing you failed to read.

06 · The mistake

We published a key that bought us nothing

Here is the decision, as it was actually written down at the time. We framed it as a fork between two identity routes:

(a) backend-registered keypair via POST /2/users/:id/public_keys — forward-only, backend can read → compatible with the features that need server-side plaintext; (b) the user's PIN unlocks full history but must stay on-device, leaving the backend blind → incompatible with the product. Choose (a).

The reasoning felt sound. Several product features needed plaintext server-side, and path (b) appeared to make that impossible. So we took the bot/server path on accounts belonging to people who use X Chat in the app. Then, during testing, a publish went through on one of them.

The symptoms arrived immediately. The owner's PIN stopped working in the X app, which reported "Registration does not exist". Every one of their contacts saw a security-code change notification. The account's two app-created versions were still listed and intact — the app just never reached them.

X later explained the mechanism exactly. The app treats the highest version as current and unlocks that one. Ours was now the highest, and it had no Juicebox registration, so there was nothing for the owner's PIN to open. X also told us the registration itself was incomplete: the official app expects the signing-key signature and registration method on the current version, and without them it keeps showing its setup or PIN prompt.

The consequence that took longest to sink in: from that moment, everyone who started or rotated a conversation with the account sealed the new conversation key to our version. Those conversations were readable only with the private key our backend held. The owner's app could not read them at all.

Four things made it worse than it had to be

  • We flagged the irreversibility and did it anyway. Our own notes said "irreversible, 5/24h, no revoke" from the very first week. Writing a warning down is not the same as building a guard.
  • We tested on a live account that someone actually uses. There was no reason it could not have been a throwaway. The bot/server path exists precisely for accounts nobody uses in the app.
  • The publish came from our test environment. When we traced it, the only identity row marked as published sat in the test environment's database, stamped the same second as the key version on X. A test deployment holding real account tokens made an irreversible change to a real account. Anything that can call a one-way endpoint is production, whatever its hostname says.
  • A safety default lied to us. The publish flag defaulted to off, and a backfill script documented as "actually publish" called the register function without it — so it minted local identities while logging success as though it had registered. When the thing that is supposed to publish doesn't, and something else does, you lose the ability to reason about what happened.

And the part that still stings

When we built the design properly — browser unlock, conversation keys sealed server-side, unattended decryption afterwards — we deleted the publishing code entirely. Not because it was risky. Because nothing needed it.

Receiving events needs a subscription. Decrypting needs conversation keys. Neither requires a key of yours to be published on the account. Path (a) and path (b) were never a trade-off between capability and safety — we just hadn't understood the SDK well enough to see that the safe path did everything.

The lesson, in one line

We spent an irreversible action, a user's chat access, and their contacts' trust — and received exactly zero capability in return.

07 · Recovery

How it gets fixed, and what survives

We reported it on X's developer forum. Their staff engaged quickly and stayed with it for four weeks. The recovery went through four stages.

1 · Freeze

X's first instructions: there is no public API to retire a published version; don't wipe or overwrite key material; stop entering the PIN in the app, because each attempt can spend a guess without fixing anything. "Frozen" took real work on our side. Background workers that harvest, decrypt, retry and demote key state are all mutations of key material, and doing nothing by hand is not the same as nothing happening. If you find yourself here, stop your workers, not just your hands — and make a PIN attempt impossible in your own app rather than merely discouraged.

2 · The suggested fix that wasn't

Three weeks in, X suggested choosing Forgot PIN at the app's prompt to set a new PIN. It did not offer a new PIN. It opened a "Forgot Passcode" screen with exactly two buttons, Reset Chat and Go Back, warning that without a passcode or a linked device the encrypted messages could not be retrieved. We stopped and asked before pressing anything, and X's first answer was to treat Reset Chat as losing the app's access to all earlier history.

3 · Measuring instead of guessing

A read-only dump of the account's published versions, next to our own key rows, settled more than any reply had:

  • Three versions: two created by the app (late 2025 and two days before the incident) and ours, the highest.
  • Every conversation key we had stored for the account was sealed to our version — exactly what "new keys go to the highest version" predicts.
  • We still held the private key for our version, so everything sealed to it was recoverable by us regardless of what happened in the app.

We sent X the versions with eight questions, and the answers changed the picture: nothing is deleted by a new version, older PIN backups stay valid with their own guess limits, other devices are left alone, old key-change events stay fetchable, and older versions can be unlocked to read their history. "Reset Chat wipes it" meant the app on that device loses access. The history itself was never at risk.

4 · Choosing the owner

That left one decision: which identity owns the account from now on. We asked about both options:

  • Keep our key, complete its registration, and give it a PIN backup ourselves with the SDK's import_keys + setup(pin) — technically possible, and X's own example code does exactly that for bot accounts.
  • Reset Chat in the app and set a new PIN, so the app creates a new version with its own registration.

X's answer was unambiguous. Because the owner wants to keep using X Chat in the official app, the app must own the identity: Reset Chat, set a new PIN in the app, and stop publishing or completing keys from the backend. A backend-completed key with a PIN set outside the app is not a supported path for the official app. Backend ownership is only supported for an account that never opens X Chat in the app.

What survives the reset

Conversation keys sealed toCoversReadable with
First app version (late 2025)Oldest historyThat version's PIN, on any device
Second app version (two days before)The two days before the incidentThat version's PIN, on any device
Our published versionFrom the incident to the resetOnly the private key our backend holds
The new app versionEverything after the resetThe new PIN, in the app and through our unlock

So the account gets its chat back and no message is lost, but the history is now split across four keys, and one slice of it can only ever be read by our server. The private key we published is no longer a liability we want to be rid of — it is the only way into those weeks. We keep it, sealed, and never publish anything for this account again.

08 · Rules

What not to do

Every item here corresponds to something that actually went wrong, for us or for another developer on the same forum.

  • ✕Never publish an identity key onto an account a person uses in the X app. Not once, not "just to test". There is no undo.
  • ✕Never publish on every sign-in. Each publish creates a new current version, and anything holding an older key stops decrypting new conversations.
  • ✕Never forget that the highest public_key_version is current. Anything you publish immediately becomes the version every new conversation is sealed to.
  • ✕Never retry a PIN in a loop, or across an account's versions. Each version has its own PIN and its own finite budget, and exhausting it is permanent.
  • ✕Never treat a juicebox_config as proof of a PIN backup. X generates one for every version on every read.
  • ✕Never treat a failed or empty key lookup as "no PIN backup". That path's remedy creates a new version and strands history — for what is usually an expired token.
  • ✕Never let a test environment hold real account tokens next to a one-way endpoint. Ours is where the publish came from.
  • ✕Never assume your DM webhook covers chat. Verify with a controlled send; silence looks identical to a broken receiver.
  • ✕Never collapse every 4xx into one error code. A full subscription cap is indistinguishable from a bad token if you do.
  • ✕Never mark an account unsubscribed from a listing you failed to read. X keeps delivering and billing.
  • ✓Do keep one identity owner per account — the app for accounts people use, your backend only for dedicated bot accounts.
  • ✓Do keep the PIN and identity in the browser and send only conversation keys to your server. It is both safer and sufficient.
  • ✓Do send a PIN only to the version the blobs are sealed to, read from the blob itself.
  • ✓Do pass data and meta.conversation_key_events together to the batch decrypt.
  • ✓Do keep any private key you ever published. It may be the only way into part of an account's history.
  • ✓Do canonicalise event ids on the envelope's snowflake, so REST and webhook deliveries of the same message agree.
  • ✓Do test irreversible operations on a throwaway account whose loss you would not mind explaining to its owner.
09 · For your LLM

The context to paste before you build this

We built this integration with heavy AI assistance, and the mistake in section 6 is one an assistant will make readily. Not because it is careless, but because X's documentation presents the two identity paths as equally available options, and nothing in the reference marks the publish call as irreversible. An assistant reading those docs will reach for the path that gives the backend more capability.

So describing the API is not enough. The context has to state what is true, not just what is possible — and it has to be phrased as prohibitions, because that is what survives being summarised into a plan three steps later. Paste this into your CLAUDE.md, your .cursorrules, or the top of your prompt before asking for any X Chat work.

X Chat integration — invariants
# X Chat (X's E2EE DM API) — rules for this codebase

## Facts that are not obvious from the docs

- Every /2/chat/* payload is ciphertext. The API has no plaintext mode. X Chat
  cannot be disabled for an account; encrypted conversations never appear in
  legacy DM lookup or DM webhooks.
- An account may have SEVERAL published identity key versions. The CURRENT one is
  always the highest public_key_version (a ms timestamp); there is no other
  "active" marker. New conversation keys MUST be sealed to each participant's
  highest version (else INVALID_IDENTITY_KEY_PAIR). The X app uses the highest
  version. Older versions are read-only history.
- Each app-created version has its OWN Juicebox registration, its OWN PIN and its
  OWN guess budget. A PIN unlocks only its own version. Older registrations stay
  valid after a newer version is created.
- Changing the passcode keeps the same version. Forgot PIN, Reset Chat and
  setup-without-recovery create a NEW version and leave the older ones in place.
- A new version never deletes messages or key-change events. X never re-seals an
  old conversation key to a newer identity: each identity opens exactly the
  history sealed to it.
- Decryption requires CONVERSATION keys, not an identity. A Chat instance
  reporting is_unlocked=false decrypts correctly when conversation keys are
  passed explicitly.
- GET /2/users/:id/public_keys returns only public_key, signing_public_key,
  identity_public_key_signature, public_key_version and juicebox_config.
  juicebox_config is generated for EVERY version on every read and does NOT
  prove a Juicebox registration exists. Registration completeness cannot be
  read back.
- Key-change events arrive in meta.conversation_key_events, separate from data,
  and the list is page-scoped.
- Account Activity (AAA) subscriptions do NOT deliver chat.* events. Chat
  realtime requires POST /2/activity/subscriptions, per user AND per event type.
- The envelope is not encrypted: encoded_event's leading Thrift fields expose
  event ids, sender id, conversation id and timestamp with no key.

## Hard prohibitions

- NEVER call POST /2/users/:id/public_keys for an account that a human uses in
  the X app, and never publish on sign-in. Publishing makes your key the
  account's CURRENT identity: the owner's PIN stops working in the app, every
  contact sees a security-code change, all new conversations are sealed to your
  key, and X exposes NO endpoint to retire a version. It cannot be undone.
- Publishing is NOT required to receive events (that needs a subscription) and
  NOT required to decrypt (that needs conversation keys). If a design appears to
  require publishing, the design is wrong. Re-read the decryption path.
- ONE identity owner per account. App-owned: the backend unlocks the app's
  highest version with the owner's PIN and never publishes. Backend-owned (bot
  accounts that never open X Chat in the app): publish a COMPLETE registration
  (public_key, signing_public_key, identity_public_key_signature,
  signing_public_key_signature, registration_method) and persist the private
  key. There is no supported way to share or copy a key between the two.
- NEVER retry a PIN automatically, and NEVER send the same PIN to another
  version's config. Read the version each pending key blob is sealed to from its
  plaintext Thrift header, send the PIN ONLY to that version, stop on the first
  invalid PIN, and surface guesses_remaining.
- NEVER treat an empty or failed public_keys response, or a juicebox_config, as
  evidence about PIN backups. The UI remedy for "no PIN backup" creates a new
  version and strands history.
- NEVER let a test environment hold real account tokens where it can reach a
  one-way endpoint.
- NEVER delete a private key for any version you ever published; it may be the
  only way to read part of an account's history.
- NEVER mark an account's subscriptions removed based on a listing that failed
  to load. X keeps delivering and billing per event.
- NEVER send the user's PIN to the backend, log it, or persist it without the
  user's explicit opt-in.

## Required implementation shape

- The identity is unlocked in the BROWSER. The browser extracts conversation
  keys and sends ONLY those to the backend, which seals them at rest. The
  backend decrypts unattended afterwards.
- Use the SINGULAR decrypt call that accepts conversation keys explicitly for
  unattended decryption. For the batch call, pass data AND
  meta.conversation_key_events together.
- extractConversationKeys does NOT verify key-change signatures. Verify them
  before storing the keys it returns.
- Extract conversation keys ONE BLOB AT A TIME. The extract call returns a flat
  {version: key} map with no conversation attached.
- juicebox_config arrives as an OBJECT; createChat calls JSON.parse internally
  and needs the STRING form. Its token_map is an ARRAY of
  {key: realmId, value: {address, token}}. Realm JWTs are scoped to
  {x_id}:{key_version} and expire in ONE HOUR — fetch them at submit time.
- Supply signing keys for BOTH participants or the other party's messages fail
  verification and are dropped.
- Canonicalise event ids on the envelope's snowflake field. REST returns a
  snowflake, the webhook returns a UUID, for the same message.
- Activity API credentials differ PER OPERATION: GET uses the app bearer (user
  token 401s), POST uses the user token, DELETE uses the app bearer with the
  user token as fallback. A 409 on create means already-subscribed — success.

## Before any irreversible call

Stop and ask the human. Irreversible here means: publishing a public key,
completing or re-publishing a registration, calling setup/delete on a Juicebox
registration, or anything that creates a new identity version. State plainly
that it cannot be undone and name what breaks for the account owner.

The last block is the one that matters most. An assistant will not spontaneously recognise that a routine-looking POST is a one-way door, because nothing in the API's shape says so. You have to tell it which doors are one-way.
